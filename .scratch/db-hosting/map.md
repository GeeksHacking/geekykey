# Map: Move GeekyKey to TiDB and Cloudflare

Label: wayfinder:map
Charted: 25 Sep 2026 by Adam, with Claude
Redrawn: 27 Sep 2026, after Julian's architecture made us the builders of two services instead of one backend

## Destination

A hand-off spec for running the GeekyKey Service and a sample Event Service (the capstone showcase event and its games) on Cloudflare Workers, with TiDB for event data and the Portal for identity. Every decision is made, and the spec ends in an ordered migration plan from today's single backend, which Adam builds in checkpoints outside this map. Due Wednesday 30 Sep 2026; anything not firm by then is marked provisional.

- **The architecture** (Julian, with Qing Guan, 27 Sep; [first diagram](assets/julian-architecture-2026-09-27.png), [station and mobile flows](assets/julian-architecture-flows-2026-09-27.png)) has three kinds of service:
  - **The Portal** only does identity: it binds tokens to users and returns the user for a token. Qing Guan owns it and its APIs.
  - **The GeekyKey Service** (Julian's "NFC Key service") is what tokens and stations reach. *Station flow:* a station sends the token's ID and its station ID; the GeekyKey Service asks the Portal for the user and triggers the Event Service directly with the user ID and station ID. An unclaimed token is a failure it handles. *Mobile flow:* tapping a token on a phone opens a GeekyKey Service link carrying the token's ID; the user logs in through the Portal, then sees the token's user info or, if it is unclaimed, claims it, and the GeekyKey Service registers the claim with the Portal.
  - **An Event Service** runs one event's games, one or several. It calls a Portal API with the user ID when an action touches the Portal, for example food collection consuming a user's food resource.
- Adam's team builds the GeekyKey Service and a sample Event Service: the capstone showcase event and its games, starting with the passport. Neither keeps a long-term database. (Julian and Adam, 27 Sep)
- TiDB holds event data, not the long-lived mapping from tokens to users. The `tokens` table may stay in TiDB until the Portal's tag APIs exist, as long as switching to them later is not painful. (Julian and Adam, 27 Sep) The Portal stores which user each token belongs to, and the GeekyKey Service sets and queries it through the Portal's APIs. (Julian, 28 Sep)

**Facts**

- The TiDB database, probed read-only on 25 Sep: TiDB Cloud Starter on Alibaba Cloud in Singapore. Both a normal connection and the serverless driver work. We log in as the cluster's root user, CHECK constraints are off, and there is no GeekyKey database yet. Details in [assets/tidb-probe.md](assets/tidb-probe.md).
- A Firebase project on the free Spark plan, with its GCP project, exists for us but is not used for hosting.
- Bot Fight Mode is off on geekshacking.com. (Julian, 27 Sep)
- The write test on 28 Sep, on a throwaway database: strict mode is on, so `ENUM` columns reject unknown values; Starter keeps `AUTO_ID_CACHE 1`; `SELECT ... FOR UPDATE` locks rows; `INSERT IGNORE` stores bad values with only a warning. Details in [assets/tidb-write-test.md](assets/tidb-write-test.md).
- Hyperdrive's MySQL support has been generally available since 7 Aug 2026, and Cloudflare's docs say it connects to "any MySQL database". TiDB is not named. The free plan allows 100,000 Hyperdrive queries a day; the paid plan has no limit.
- The Workers free plan allows 100,000 requests a day and 50 outside requests per incoming request; the paid plan allows 10,000 per request. TiDB Starter's free allowance is 50 million Request Units a month, and once it is used up TiDB refuses new connections. Sources in "How do stations talk to the GeekyKey Service?".
- A Worker can call another Worker on the same zone only through a service binding or at its Custom Domain, and each binding call counts as an outside request. A Worker's `fetch()` follows redirects and sends `Authorization` on, even to another domain. Invocation logs capture request headers; whether `Authorization` is hidden is not documented. Sources in "How does the GeekyKey Service trigger an Event Service, and know which one a station belongs to?".
- `GeeksHacking/geekykey` is private, in an organization on GitHub Free, so `main` can't be protected and a workflow on any branch can read the repo's secrets. Six people have write access; Julian and Qing Guan are admins. Julian is fine with making it public (28 Sep), which unlocks branch protection and environment secrets; a Wi-Fi password committed in `firmware/NFC_test/test.ino` has to be changed first. Sources in "How do deploys and secrets work?".
- GeeksHacking's Cloudflare account is on the free plan, and Julian wants to try the free tier before paying (28 Sep). Its `workers.dev` subdomain is `geekshacking.workers.dev`. Since 28 Sep the Portal accepts several redirect URLs per OAuth app. Qing Guan or Julian adds our custom domains, and Qing Guan advised one level of subdomain because Cloudflare's free zone certificate covers only one level.
- The showcase is on Wed 18 Nov 2026, with setup on Tue 17 Nov, at Ngee Ann Polytechnic. (Adam, 28 and 29 Sep)
- Cloudflare's per-Worker roles (15 Sep 2026) let Julian give each person or API token Metadata Read-Only, Content Read-Only, Editor or Admin on chosen Workers; creating a Worker needs Admin across all of them, and attaching a custom domain needs write access to the zone's Workers routes. A preview's service binding calls the bound Worker's production deployment. `wrangler deploy` overwrites settings and routes changed in the dashboard, but never secrets. Sources in "How do deploys and secrets work?".
- The Portal, read from its public repo on 28 Sep: it runs as one Cloud Run instance in Singapore that handles one request at a time and sleeps when idle, so a request can queue behind others or wait for a cold start, and fails with `429` after about 10 seconds. It already offers the client-credentials flow for services. Its draft `NfcTag` gives each tag a new GUID as its ID and has no endpoints yet. User IDs are GUIDs. Sources in "What does the GeekyKey Service need from the Portal's tag APIs?".
- TiDB Starter's free backup, checked 29 Sep: one a day at a random time, kept one day, no manual backups, and a restore always makes a new cluster without our logins. Workers Logs on the free plan keep 200,000 events a day for 3 days. Sources in "How do we back up the database, recover it on event day, and clear the test data before the doors open?".
- The free plan's security features, checked 29 Sep: the zone gets one rate limiting rule, which matches only the path, counts per IP address and blocks for 10 seconds, and five custom rules, which can match a hostname and skip Browser Integrity Check, Security Level and rate limiting. Browser Integrity Check is on by default; geekshacking.com lets the station's `ESP32HTTPClient` user agent through today. The Workers rate limiting binding counts any key we choose over 10 or 60 seconds, per Cloudflare location and roughly. Zone rules don't cover `workers.dev` or preview addresses. Sources in "How do we protect our public addresses without blocking the stations?".
- Watching on the free plans, checked 29 Sep: Cloudflare's Health Checks start on Pro; the free plan allows 5 Cron Triggers for GeeksHacking's whole account; the day's request allowance resets at 08:00 Singapore time; the Workers Observability dashboard saves and shares queries but doesn't alert. TiDB Starter has no built-in alerting. The heartbeat proves a station's Wi-Fi and key, not its reader. Sources in "How do we notice trouble on event day, and who watches?".

- [Can the architecture carry the 24 Sep game ideas?](issues/04-future-ideas-fit.md): all of them fit; live interaction would add a Durable Object, and trading needs transactions to stay available.
- [How is the frontend set up, and how does the browser reach the backend?](issues/05-frontend-setup-and-routing.md): a Worker with static assets that forwards `/api` and `/auth` to the backend through a service binding, so the browser sees one address and there is no CORS; stations call the backend directly. *Partly superseded by the 27 Sep redraw:* serving screens from a Worker that forwards to its backend still holds; one backend, and stations calling it directly, do not.
- [Which hostnames, and which OAuth redirect URLs?](issues/06-hostnames-and-oauth-redirects.md): the frontend is `geekykey.geekshacking.com` and the backend `api.geekykey.geekshacking.com`; Julian gets three redirect URLs (localhost, the frontend's `workers.dev` address until the subdomain exists, and the final one), and the backend reads its redirect URL from a setting. *Partly superseded by the 27 Sep redraw:* `geekykey.geekshacking.com` becomes the GeekyKey Service's address and the redirect URLs stand; where the passport's screens live, and whether `api.geekykey.geekshacking.com` is still needed, move to the new tickets. *Renamed 28 Sep:* the stations' address is `geekykey-api.geekshacking.com` ("How do deploys and secrets work?").
- [Which parts of today's backend belong to the GeekyKey Service, and which to the Event Service?](issues/12-backend-split.md): the GeekyKey Service checks stations, looks up tokens and hands each tap on as a user and station; the Event Service stores taps, drops replays, applies the cooldown and owns stamps, points and per-event users. A station feeds one Event Service, which picks the games. Token IDs never leave the GeekyKey Service. One TiDB database for now, tables kept apart by service; move first, split second.
- [How is the database set up?](issues/07-database-setup.md): Drizzle over `mysql2` through Hyperdrive, provisional until a deployed Worker proves it; the cooldown locks the station's row in a transaction; `ENUM` columns, ISO-string timestamps and `AUTO_ID_CACHE 1` on taps; an app login and a migration login; migrations run from outside the Worker before each deploy; no foreign keys between the services.
- [How do local dev, tests and CI get a runtime and a database?](issues/08-dev-test-ci.md): Deno leaves; `wrangler dev` runs the backend in workerd and Vitest with Cloudflare's plugin tests it there, provisional until the first checkpoint; laptops and CI run TiDB v8.5.3 in Docker from one `compose.yaml` (ready in about 1.5 s, under 500 MiB); tests share one `geekykey_test` database; the Vite proxy stays; after the split, two packages and an end-to-end smoke test on every pull request.
- [What is a token's ID, and what URL is written on each token?](issues/13-token-id-and-url.md): the hardware UID; every token carries `https://geekykey.geekshacking.com/t/<UID>`, filled in by the chip's UID mirror, and is write-protected by one password; Zi Tao writes them with a writer sketch; the token page shows others only that a token is taken; guessable addresses are accepted. Recorded as ADR 0001.
- [How do stations talk to the GeekyKey Service?](issues/11-station-endpoints.md): stations call `geekykey-api.geekshacking.com` (renamed from `api.geekykey.` on 28 Sep) over HTTPS, trusting 14 root certificates for Cloudflare's CAs, with today's requests and station key unchanged; a key can be replaced keeping the station's ID; new `no_event` status for a station that feeds no event, including taps timed before its current link; `503` means keep and resend; a 60-second heartbeat sets the clock and keeps the connection open; each result shows about 2 seconds, amber only for `cooldown`, with no pause between taps. A message to Zi Tao carries it.
- [How does the GeekyKey Service trigger an Event Service, and know which one a station belongs to?](issues/14-event-service-triggers.md): the hand-off is one HTTP request, over a service binding to our sample and HTTPS to other teams', typed by Zod schemas in `packages/handoff`; the list of Event Services lives in the GeekyKey Service's settings, and each station's link is two columns on `stations`, changed only by GeekyKey admins; a new `no_game` status; 3 seconds, then `503`; one Event Service key each way; an Event Service reads its stations' status over HTTPS.

## Not yet specified

The spec marks both of these provisional (Adam, 28 Sep), in its section 11.

- **Staying on the free plan.** The account is on the free plan until the numbers say otherwise, with the decision on Paid due by 11 Nov 2026, a week before the showcase ("How do deploys and secrets work?"). The first deploy measures what a passport poll and a tap cost in Hyperdrive queries, Workers requests and outside requests, to estimate the showcase's day against 100,000 queries, 100,000 requests and 50 outside requests per request. The passport alone could use up Hyperdrive's allowance in about 55 passport-hours. Ways to fit: fewer queries per poll, polling only while the passport is on screen, slower polling, or a push design through a Durable Object, which Qing Guan suggested; the mentors ruled out live sockets on 24 Sep unless a game needs them, so push would go back to them with cost as the reason. Or pay: Workers Paid starts at $5 a month. Also TiDB Starter's free allowance of 50 million Request Units a month, after which it refuses new connections: TiDB's console shows what a day of polling and station heartbeats costs after the first deploy. A TiDB spending limit above $0 would also keep backups up to 30 days at a chosen time, instead of one day at a random time. Rate limits stop one misbehaving caller but not a flood from many addresses, which could still use up the free day; that risk counts toward paying. A heartbeat costs one query, since the station's key is found in memory ("How do we protect our public addresses without blocking the stations?"). The rehearsal on production, by 7 Nov, gives a whole day's numbers before the decision, and comes out of November's TiDB allowance. If we're still on the free plan on 18 Nov, Adam checks the counters hourly from 08:00 and Julian upgrades at 70% ("How do we notice trouble on event day, and who watches?").
- **After the event.** What happens to an Event Service's data once its event ends. Julian suggested keeping a per-event copy of user details and deleting it afterwards. With one database for now, deleting the event's data also takes the `tokens` stand-in and the stations, so the claims must first be copied to the Portal, as planned in "What does the GeekyKey Service need from the Portal's tag APIs?". Unlinking the event's stations afterwards is a GeekyKey admin's job. The end-of-day copy on Adam's laptop feeds Joshua's analysis and the claims copy, and our copies are deleted along with the event's data.

## Out of scope

- **Station offline sync, 4G and battery power.** Zi Tao owns station connectivity. The backend already accepts late batch uploads, deduplicated by `client_tap_id`.
- **Encrypting the stations' flash.** It burns permanent eFuses and the firmware is Zi Tao's. A station that goes missing has its key replaced instead ("How do we protect our public addresses without blocking the stations?").
- **Building live sockets.** We keep polling unless a core game mechanic needs them (mentors, 24 Sep). Whether the architecture leaves room for them is part of "Can the architecture carry the 24 Sep game ideas?".
- **Building the Portal's tag APIs.** Qing Guan's, still being agreed on 27 Sep; Adam will pass on new developments. It also answers whether tokens stay linked to people after the event: they do, in the Portal.
- **Other teams' Event Services.** Julian wants future teams to build Event Services on the GeekyKey Service without touching the Portal. This map plans only our sample, but the way the GeekyKey Service triggers an Event Service must also work for one outside our Cloudflare account.
- **Entry, exit and food stations.** Not a client priority (24 Sep).
- **Renaming "barrel key" to "API key".** It has its own action item, and the code and docs keep "station key".
- **Moving data from the dev database.** It only holds test data.
- **Deploying the updates site.** The mentors' timeline isn't part of the destination. It can reuse whichever way Julian picks in "How do deploys and secrets work?".
- **Hosting on GCP or Firebase.** Julian chose Workers on 25 Sep.
- **Portal login details** (OIDC issuer, client ID, claims). Still an open question with Qing Guan in the API agreement. Only the redirect URLs are in scope here.
